The evaluation programs are the part of `agents/` that actually runs agents against environments.

The easiest way to run an evaluation is through the CLI:

```bash
gym-anything benchmark moodle --task enroll_student --agent ClaudeAgent --model claude-opus-4
```

<Callout type="info">
Run `gym-anything agents` to see which agent names are available.
</Callout>

## One Agent, One Task

Run a single agent on a single task:

```bash
gym-anything benchmark moodle --task enroll_student --agent ClaudeAgent --model claude-opus-4
```

The important arguments are:

- `env_dir`: environment name (e.g. `moodle`) or full path
- `--task`: task id inside that environment
- `--agent`: agent class name (e.g. `ClaudeAgent`)
- `--model`: model identifier (e.g. `claude-opus-4`)

Common optional arguments are:

- `--steps`: maximum number of agent steps (default: 50)
- `--seed`: reset seed (default: 42)
- `--temperature`: sampling temperature
- `--agent-arg KEY=VALUE`: extra agent arguments (repeatable)
- `--use-cache`, `--cache-level`, `--use-savevm`
- `--fast-io`: enable runner-native fast screenshot/input paths
- `--disable-thinking`: pass `chat_template_kwargs.enable_thinking=false` to
  OpenAI-compatible VLM calls
- `--post-reset-observation-delay`: wait this many seconds after `env.reset`
  before capturing the first model observation
- `--post-step-observation-delay`: after each `env.step`, wait this many
  seconds and capture a fresh observation for the next model turn
- `--timing-jsonl`: write per-iteration timing records to a chosen JSONL path;
  by default single-task runs write `timing.jsonl` and `timing_summary.json`
  under the episode directory

For `Qwen3VLAgent`, `Qwen35VLAgent`, `Qwen35RealAgent`, `Qwen35DSLAgent`,
`Qwen35DSLActionAgent`, `KimiAzureAgent`, and `KimiDistillAgent`, processed
screenshots are encoded in memory before the VLM call and image artifacts are
written asynchronously by default. The default payload/artifact format is JPEG
quality 85; override with `--agent-arg image_format=png`,
`--agent-arg jpeg_quality=90`, or `--agent-arg async_image_save=false` when you
need a different behavior. The same defaults can be controlled with
`GYM_ANYTHING_AGENT_IMAGE_FORMAT`, `GYM_ANYTHING_AGENT_JPEG_QUALITY`, and
`GYM_ANYTHING_AGENT_ASYNC_IMAGE_SAVE`.

`Qwen35DSLAgent` uses the compact CUA-DSL response format and defaults to
incremental session transport. Each run gets a generated session ID and sends
only the new messages for that turn: the first request sends `system + user`,
then later requests send `assistant + user` deltas. Override with
`--agent-arg incremental_messages=false`, `--agent-arg session_id=<id>`, or
`GYM_ANYTHING_AGENT_SESSION_ID=<id>`.

For servers that accept raw RGB image payloads, pass
`--agent-arg image_format=prime_rgb`. The request payload uses
`data:application/x.prime-rgb;w=960;h=540;base64,...`; the saved artifact in
`all_runs/.../observation_*.jpg` remains a viewable JPEG. Override the raw
dimensions with `--agent-arg prime_rgb_width=<w>` and
`--agent-arg prime_rgb_height=<h>`.

For vLLM servers that support image UUID caching, pass
`--agent-arg image_cache_uuids=true` or set
`GYM_ANYTHING_AGENT_IMAGE_CACHE_UUIDS=1`. The first request that contains a
frame sends both `uuid` and image bytes. Later requests reference old frames as
`{"type": "image_url", "uuid": "...", "image_url": null}` while still sending
bytes for the newest frame. This is a vLLM extension and is disabled by default
for compatibility with standard OpenAI-compatible servers.

## What `run_single` Does

At a high level, `run_single` does this:

1. load the environment and selected task
2. reset the environment
3. create the agent class you selected
4. call `agent.init(...)`
5. capture an observation
6. repeat:
   - call `agent.step(obs, action_outputs)`
   - send the returned actions to the environment
   - feed the action results back into the agent
7. finish the task with `mark_done=True`
8. close the environment
9. call `agent.finish(...)`

Single-task runs also write timing records. The outer loop records environment
creation, reset, initial capture, each policy iteration, and each `env.step`.
Agents can add an `agent.last_step_timing` dictionary for internal policy
breakdowns such as image processing, message construction, VLM call time, and
response parsing.

If you're trying to understand how the loop works, `agents/evaluation/run_single.py` is the file to read.

## One Agent, Many Tasks

Omit `--task` to run all tasks in a split:

```bash
gym-anything benchmark moodle --agent ClaudeAgent --model claude-opus-4 --split test
```

To run across all environments:

```bash
gym-anything benchmark all --agent ClaudeAgent --model claude-opus-4 --split test
```

The main arguments for batch mode are:

- `--split`: task list name such as `train`, `test`, or `all` (default: `test`)
- `--surface`: `raw` or `verified` (default: `raw`)

<Callout type="info">
Each task runs in its own process for fault isolation — if one task crashes, the rest continue.
</Callout>

<Callout type="info">
If you're only trying to verify that an agent works at all, start with a single task before running batch mode.
</Callout>

## If You Want To Change The Loop

Read the evaluation files in this order:

1. `agents/evaluation/run_single.py`
2. `agents/evaluation/run_batch.py`
3. `agents/evaluation/setup.py`

`run_single.py` is the main loop. `run_batch.py` is mostly task selection plus repeated calls into `run_single`.
