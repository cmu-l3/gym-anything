1 The Problem

Computer-use agents (CUAs) promise to automate digitally intensive occupations that collectively represent trillions of dollars in GDP. But current benchmarks test agents on short-horizon tasks (changing wallpapers, filling web forms) over a narrow set of consumer apps, revealing little about whether agents can handle real professional work. Existing interactive benchmarks cover at most 20 software applications and a handful of occupation groups.

The root cause: creating realistic environments requires installing software, configuring it with domain-appropriate data, designing tasks, and verifying everything works. This demands weeks of expert effort per application, naturally limiting benchmark scale. As a result, both evaluation is unfaithful (high scores say little about real-world capability) and training signal is limited (short tasks over few apps cannot produce the diverse trajectories needed for real work).

Read more: why existing benchmarks fall short

Real-world workflows are long-horizon and take place in heterogeneous environments, often requiring hundreds of steps across diverse software configured with domain-specific data. For instance, end-to-end analysis of a medical imaging dataset requires a radiology tool set up with annotated clinical CT scans, while reconciling financial records across an ERP system requires software populated with transaction histories and vendor accounts. No existing benchmark provides this kind of realistic, domain-grounded evaluation.

Existing benchmarks fall into two categories, each with fundamental limitations. Static datasets (Mind2Web, AITW, AndroidControl, OmniACT) collect thousands of episodes but evaluate via action-matching rather than execution, penalizing valid alternative strategies. An agent that accomplishes the same goal through a different but equally correct sequence of actions would be marked as wrong.

Interactive benchmarks provide execution-based evaluation but cover narrow slices of the software landscape. Web benchmarks (MiniWob++, WebArena, VisualWebArena, WorkArena) are restricted to a few websites. Desktop benchmarks span at most a handful of applications with manually authored environments: OSWorld covers 9 software with 369 tasks, WindowsAgentArena covers 11 software with 154 tasks, and others like Spider2-V, AssistGUI, TheAgentCompany, and ScienceBoard are similarly limited. AndroidWorld covers 20 apps.

Critically, all interactive benchmarks rely on manual environment creation, which inherently limits their scale. None simultaneously provides training data, long-horizon tasks, or broad occupational coverage. This leads to two consequences. First, evaluation is unfaithful: high scores on these narrow benchmarks reveal little about whether an agent can handle real-world professional work. Second, training signal is limited: short-horizon tasks over a small number of applications cannot produce the diverse, long-horizon trajectories needed to train capable agents.

The root cause behind all of these limitations is that each software application requires installation, configuration with domain-appropriate data, task design, and verification. This process often demands weeks of expert effort per application, creating a fundamental bottleneck that manual approaches cannot overcome.

2 The Gym-Anything Library

Our key idea is that creating computer-use environments is itself a coding and computer-use agent task. Setting up software requires writing installation and configuration scripts (a coding task). Verifying the running environment through screenshotsVisual grounding as verification. The creation agent uses visual grounding to check each screenshot against the expected application state, catching discrepancies that text-based logs miss (e.g., a login screen still visible, placeholder data in fields, or a crash dialog). This is the same observation modality that evaluation agents will later use, ensuring consistency between creation and evaluation. and checking the screen is a computer-use agent task.

Scaling this to hundreds of software applications requires handling substantial heterogeneity: different applications need different operating systems, databases, and network configurations. The Gym-Anything library addresses this by reducing every environment to a standardized specificationThree setup scripts + a config file. The scripts are staged: install (software + dependencies), configure (realistic data + settings), and task setup (starting state for a specific task). Multiple tasks share the same install/configure scripts, varying only the task setup. The config file specifies OS image, resource limits, and interfaces.: a small set of setup scripts and a configuration file. This enables an AI agent to create environments by writing only software-specific scripts, while the library handles container orchestration, display forwarding, and multi-OS support across Linux, Windows, and Android.

Previous works (OSWorld, VisualWebArena) constructed environments manually by interacting with an actual operating system and then taking VM snapshots. These snapshots cannot be inspected, version-controlled, or partially reused across tasks. Modifying anything requires repeating the entire manual setup from scratch, limiting modularity, reproducibility, and scalability.

In the Gym-Anything library, each environment is defined by three sequential setup scripts and a declarative configuration file. The scripts progress from general to task-specific: install (software and dependencies), configure (realistic data and settings), and task setup (specific starting state for a given task). Multiple tasks for the same software share the same install and configure scripts, varying only the task setup. For example, creating a LibreOffice Calc environment requires only an install script (e.g., apt-get install libreoffice), a configure script that downloads a sample spreadsheet, and a config file specifying the OS image and resource limits. The library handles container orchestration, display forwarding, and checkpoint management automatically.

Users and AI agents interact with any environment through a standard gymnasium-style API that provides a unified observation space (screenshots) and action space (keyboard and mouse inputs). The library handles display forwarding and input translation across operating systems, abstracting away the differences between Linux, Windows, and Android. It also supports multiple compute backends, including Docker for standard deployments and Apptainer for rootless systems such as SLURM clusters.

The staged design enables caching at each stage boundary, so creating new tasks for an already-configured application only requires re-running the task-specific setup script. Combined with network-process-file isolation between containers, this enables massive parallelization: in our experiments we run 400+ concurrent environments across 1,600 CPUs.

The specification is simple enough that an LLM agent can author environments autonomously, yet expressive enough to capture complex, production-grade software configured with realistic data, from desktop image editors to multi-container enterprise systems.

3 Creation-Audit Loop

Without external verification, current agents (including frontier models) prompted to create environments frequently produce incorrect setups: using placeholder data instead of real datasets, leaving software at installation wizards, or claiming the environment is ready without ever launching it. The common thread is that the agent's claims about what it has done are not reliable, but the actual state of the environment is: a screenshot reveals whether the software is running or stuck on a crash screen, regardless of what the agent claims.

We exploit this through a creation-audit loopTwo agents, adversarial separation. A creation agent (Claude Opus 4.5/4.6 via Claude Code) writes setup scripts, downloads real-world data (public medical datasets, email corpora, financial schemas), launches the software, and produces evidence (screenshots, logs). An independent audit agent then inspects this evidence against quality checklists and reports issues. The loop runs for multiple iterations.: a creation agent builds the environment and produces evidence of correct setup, then an independent audit agent verifies this evidence against a quality checklist and reports issues for iterative correction. The creation agent also maintains a shared memoryA growing directory of reusable knowledge. Contains both software-specific notes (e.g., "LibreOffice needs headless mode disabled for GUI tasks") and general patterns (e.g., "always poll service readiness before launching multi-container web stacks"). Every L environments, a summarization agent condenses common patterns to keep memory manageable. This enables sublinear growth in creation time: later environments benefit from lessons learned on earlier ones. of common fixes and patterns, enabling sublinear growth in creation time as more environments are built.

The creation agent is a coding agent equipped with bash, python, and computer-use tools, with complete access to the library and all previously created environments. Given a new software name, it first researches how the software should be configured, finds and downloads real-world data (e.g., public medical imaging datasets for radiology software, published email corpora for messaging clients), studies similar previously created environments, then implements setup scripts, launches the environment, takes screenshots, uses visual grounding to check the application reached the expected state, and iteratively debugs failures. Crucially, the agent must produce evidence: screenshots of the running software, execution logs, and other verifiable artifacts.

Separating the creation and audit roles offers three key benefits: (a) it removes self-confirmation bias, (b) the written audits ensure interpretability, letting humans independently verify quality, and (c) the adversarial framing catches cases where the creation agent made self-misleading claims. The audit agent acts as an adversary: it analyzes screenshots and logs, inspects actual config and script files, and if necessary actually runs the environment. It outputs a structured audit detailing what is correctly implemented and what the critical issues are.

We tested this empirically with a cross-model auditing experiment. Both self-audit and cross-model audits detect all critical issues, but cross-model audits identify on average 2.1 additional issues per environment. For example, on OpenELIS (a lab information system), the self-audit accepted patient data as realistic, while the cross-model audit inspected the seeding script and discovered the data was a hardcoded Python list, directly contradicting inline comments claiming real-world WHO/CDC sourcing. On Visallo (a link analysis platform), the cross-model audit caught a file path mismatch: a CSV file claimed to be "on the desktop" was actually placed in /home/ga/Documents/.

A recurring challenge is context fatigue. After processing hundreds of thousands of tokens, the creation agent often declares the task done prematurely because it loses track of remaining requirements. To address this, whenever the agent stops, we re-prompt it to reread the setup guidelines and checklists and complete any requirements it may have skipped. This simple nudge recovers many omissions that would otherwise go undetected.

The shared memory is effectively a directory of files that grows over time, initialized with the hand-written prompt. After each environment, the agent documents what worked and what failed, updating software-specific notes and general notes. For example, one agent discovered that a multi-service web platform needed readiness polling before the GUI could launch; this became the default pattern for all subsequent web stacks. Every L environments, a memory summarization agent reads through all memory files, identifies common patterns, and condenses them to keep the memory manageable.

Read more: GDP attribution formula and top software

The full pipeline proceeds in seven steps. First, we estimate GDP per occupation using employment count multiplied by mean wage, scaled to national GDP. Second, we discover software used per occupation using an LLM with web search, producing approximately 16,600 software entries across roughly 1,400 categories. Third, we clean the catalog by deduplicating categories and removing hallucinated entries via web-grounded verification. Fourth, we attribute GDP to individual software.

GDP is attributed to individual software via: GDP_software = Σ GDP_occ × p_computer × s_category × s_software, where p_computer is the fraction of the occupation's work involving computers (from occupational surveys), s_category is the share attributed to a software category (e.g., "spreadsheets" for an accountant), and s_software is the individual software's share within its category.

Top software by attributed GDP: Microsoft Excel ($1.81T, used by 582 occupations), Microsoft Word ($1.27T), Google Chrome ($1.05T), Microsoft Outlook ($0.94T), and Visual Studio Code ($50.4B). Since these are commercial and cannot be self-hosted, we substitute them with the closest free alternative from the same category.

The fifth step filters to sandboxable candidates: self-hostable, free, GUI-based, and requiring no specialized hardware. Of the approximately 16,600 catalogued software, only about 3,400 pass this filter. In the sixth step, high-GDP software that cannot be sandboxed (e.g., Bloomberg Terminal at $79.5B, Salesforce, Epic EHR) is substituted with the closest sandboxable alternative from the same category.

Finally, we apply tiered selection across five tiers to balance economic impact and diversity: (1) highest-GDP software overall (100 budget), (2a) strategic domains including Healthcare, Education, Protective Services, and Transportation (100 budget), (2b) STEM fields including Architecture/Engineering, Computer/Math, and Life/Physical/Social Science (100 budget), (3) round-robin across all 22 SOC groups for approximately 5 per group (116 budget), (4) niche occupation-specific software (44 budget), and (5) uncovered software categories ranked by GDP (40 budget). The output is approximately 500 selected software, of which 200 are built based on the available compute budget.

5 Task Generation

An LLM can generate reasonable task descriptions, but without actually running the software, the generated environment configurations are often incorrect. To address this, we follow a propose-and-amplify5 expensive seeds + 75 cheap amplifications per software. The proposer (Claude Opus via Claude Code) creates ~5 seeds by actually running the software, downloading real data, interacting through the GUI, and verifying results. The amplifier (Gemini 3 Pro) then generates ~75 more, receiving all previously generated tasks as context to enforce diversity. A VLM filter launches each generated task and checks whether the starting state matches the description, discarding failures. This yields 12,103 tasks total. strategy: an agentic model first proposes a small number of seed tasks per software by actually running it and verifying the results. A non-agentic LLM then amplifies these seeds into a larger set using the seed implementations as in-context examples, followed by automated VLM-based filtering. Tasks amplified from seeds achieve an 88.9% setup success rate vs. 55.2% without seeds.

Read more: task quality guidelines and what happens without seeds

The proposer follows guidelines across three dimensions: realism (does the instruction reflect a genuine, real-world use case?), difficulty (does the task require a long-horizon, multi-step trajectory to solve?), and diversity (do the tasks cover varied functionalities of the software?). These guidelines ensure that generated tasks reflect the kind of work professionals actually do, rather than toy demonstrations of software features.

The agentic loop in the proposer is necessary because the model must actively run the software, search for and download or generate realistic data, interact via the GUI, and verify the resulting state. This expensive step occurs only once per software but is essential for producing high-quality seed tasks. The proposer generates approximately 5 seed tasks per software.

To enforce diversity during the amplification phase, tasks are generated sequentially: the model receives all previously generated instructions 1, ..., t as context when producing task t+1. Semantic similarity filtering then discards duplicates. The amplifier generates approximately 75 tasks per software using the seed implementations as in-context examples.

After generation, automated filtering launches each generated task, captures the starting state observation, and passes it alongside the instruction to a VLM. The VLM checks whether the starting state matches the expectation from the task description. Tasks that fail this check are discarded. After filtering, the pipeline yields 12,103 tasks across all 200 software applications.

Qualitative analysis on three representative software (Firefox, AstroImageJ, and Moodle) reveals that without seeds, the model defaults to demonstrating software features rather than generating realistic professional workflows. In particular, it produces shorter-horizon tasks and writes less thorough setup scripts. The seed examples effectively anchor the LLM toward the right level of complexity and realism, which is why the seed-based approach achieves an 88.9% setup success rate compared to 55.2% without seeds.

The VLM verifier uses privileged information alongside the task instruction to generate a granular checklist C = {(c_i, w_i)}, where each c_i defines a specific subtask to verify and w_i is its point value. The verification score is computed as V(τ) = Σ w_i · VLM(τ, c_i, I), yielding a score from 0-100 rather than binary pass/fail. This enables partial credit for tasks where the agent completes some steps correctly but not others.

The privileged information I is extracted automatically by a separate coding agent that parses the setup scripts and retrieves or searches online for the relevant ground truth. For example, in a medical imaging task, the correct tumor location is known from the downloaded dataset. In a financial task, the expected account balances are determined by the initialization data. In a clinical decision support task, the expected drug interactions are known from the loaded formulary. This eliminates the need for manual annotation of ground-truth answers.

The programmatic approach performs poorly primarily because the model writes incorrect scripts that fail to parse the data formats present in the end state. Per-item checklist agreement with human annotations is 90.9%, confirming that the granular decomposition into subtasks is well-calibrated.

The integrity checklist evaluates three conditions: (a) the intended software was used, (b) the required state was reached through the software's own interface rather than by directly editing config or data files, and (c) the agent did not exploit environment artifacts. Failing any integrity item sets V(τ) = 0 regardless of how many task subtasks were completed.

Across approximately 3,000 Gemini-3-Flash trajectories, integrity checks flag only ~1.5% of high-scoring runs (score >75), producing 21 flags total, of which 15 are true positives. Two representative cases illustrate the subtlety of these violations. On Autopsy (digital forensics software), the agent followed the correct forensic workflow but fabricated hash values in its final report rather than copying the values actually visible in the application. On Epi Info (epidemiology software), the agent mistyped an input parameter, causing the tool to display an incorrect result, but then wrote the mathematically correct answer in its output, a value that was never shown by the tool.

7 CUA-World

The result is CUA-World: 12,103 tasks across 200 software applications spanning domains from medical science and astronomy to engineering and enterprise systems, each configured with realistic data, across three operating systems, with train and test splits. It is the first benchmark to simultaneously provide interactive environments at scale, support long-horizon evaluation, cover all 22 SOC occupation groups, offer automated environment creation, and include a training split.

We also construct CUA-World-Long: 200 particularly challenging tasks (one per software) designed through trajectory-guided analysisFailure-driven task design. For each software, we generate trajectories from a strong agent on existing tasks, then analyze why certain tasks have lower pass rates and what the common failure modes are. For instance, on 3D Slicer (medical imaging), we discovered agents get stuck in a "scrolling loop", endlessly scrolling through image slices looking for the "perfect" anatomical level without ever committing to placing a measurement. The generated Long task specifically exploits this weakness. of agent failure modes. These tasks often require over 500 steps, far exceeding existing benchmarks. All 200 tasks are manually verified against 8 quality criteria.

Contamination filtering: To prevent data leakage between train and test splits, we treat tasks as nodes in a similarity graph, with LLM-graded similarity scores (on a 1-8 scale) as edges. Any pair scoring 4 or higher ("very similar") is flagged. We compute connected components and assign entire components to a single split, ensuring no contaminated pairs cross the boundary. Manual verification shows the pipeline is conservative: it flags several non-contaminated pairs but misses very few true contaminations.

CUA-World-Long generation follows a trajectory-guided strategy. For each software, we generate k trajectories from a strong agent on existing tasks, then analyze those trajectories to identify failure patterns and generate harder tasks that specifically exploit discovered weaknesses. The agent receives 8 quality guidelines covering real-world relevance, objective evaluability, realistic data, and other criteria. All 200 Long tasks are manually verified against these quality criteria, and tasks that fail verification are iteratively refined through further agent interaction.

For example, on 3D Slicer (medical imaging software), analysis of 34 agent trajectories showed a 0% pass rate. The primary failure mode was a "scrolling loop" where the model gets stuck endlessly scrolling through image slices looking for the "perfect" anatomical level, never committing to placing measurements. The highest-scoring existing task (tumor_ventricle_proximity, scoring 31/100 points) succeeded only because data was pre-loaded with structures already visible, so the model immediately placed a measurement without extensive scrolling. The generated Long task specifically exploits this weakness.

These Long tasks often require more than 200 steps for human completion. Current models frequently fail even after 500 steps, and the overall mean across all Long trajectories is 425 steps, far exceeding the typical step counts in existing benchmarks.

Performance scales log-linearly with data

This suggests further scaling the Gym-Anything pipeline could yield even stronger models. See the interactive charts on the project page.

Generalization to unseen software is limited

Models trained on 25-50% of the 200 software recover 65-87% of full-training gains on software seen during training (IID), but only 22-27% on unseen software (OOD). This means training on a specific software helps substantially, but training on other software also contributes. The gap underscores the need for scalable environment creation across diverse software.

Test-Time Auditing improves long-horizon performance

Pass rate on CUA-World-Long scales with step budget: 2.0% at 50 steps, 6.5% at ~200 steps, 11.5% at ~1,300 steps. Adding Test-Time AuditingMirrors the creation-audit loop at inference time. Whenever the agent signals task completion, an independent VLM reviews the full trajectory without seeing the agent's chain-of-thought. It provides structured feedback on what remains incomplete, and the agent resumes work. This catches premature stops, a common failure mode where agents declare "done" despite unfinished subtasks. Under this scheme, agents sometimes work continuously for over 12 hours on a single task. further improves pass rate to 14.0% under the same 2,000-step cap by catching premature stops.

Why agents fail: retry loops and missing verification

Analysis of ~3,000 trajectories reveals that failed trajectories spend 78% of their steps in retry loops (vs. 39% for passed). Verification checks, where the agent re-inspects its work, are present in 91% of passed trajectories but only 70% of failed ones. This provides empirical motivation for Test-Time Auditing.

Teacher selection paradox: Opus 4.6 is the strongest teacher model with a 53.5 average score, while Kimi-K 2.5 is one of the weakest at 39.8. Yet Kimi-K 2.5 produces the best student models: 25.3 vs. 19.3 (Opus) for Qwen3-VL-4B, and 15.8 vs. 9.8 (Sonnet) for Qwen2.5-3B. A possible explanation is that Kimi-K 2.5 is open-source and provides full reasoning chains in its trajectories, giving the student model richer learning signal despite the teacher's lower raw performance.

Trajectory length curriculum: We compared training on 50-step vs. 200-step trajectories under the same $25/software budget. On average the results are similar (22.7 vs. 23.8), but the optimal length varies by software: 50-step trajectories perform better on GIMP and 3D Slicer, while 200-step trajectories are better on OpenEMR, which has longer-horizon tasks. Based on these findings, we adopt a two-stage curriculum: first train on 50-step trajectories, then continue on full 200-step trajectories.

Visual complexity bottleneck: Large models (Gemini, Kimi) maintain consistent pass rates across visual complexity levels (25.3%, 20.9%, 21.6% for Gemini across low, medium, and high complexity). In contrast, small models show steep declines: Qwen3-VL-2B drops from 3.2% on low-complexity to 0.0% on high-complexity software. Distillation improves performance at all visual complexity levels but does not close the gap, suggesting that visual understanding remains a fundamental bottleneck for smaller architectures.

Domain knowledge: All models decline in performance from general to specialized software. The decline is steeper for small models (roughly 3x: 6.4% to 2.2%) than for large models (roughly 1.3x: 25.6% to 19.9%). This indicates that domain-specific knowledge presents a greater challenge at smaller scales, where the model has less capacity to retain specialized information.

Behavioral patterns: Automated analysis of approximately 3,000 trajectories reveals 15 canonical behavior patterns. The largest gap between passed and failed trajectories appears in retry loops: failed trajectories spend 78% of their steps retrying actions compared to only 39% for passed trajectories. UI exploration (navigating menus, searching for the right interface element) dominates for both outcomes at 67-76% of steps, indicating that most agent effort is spent locating the right interface elements rather than executing the core task. Notably, verification checks (where the agent pauses to confirm its progress) are present in 91% of passed trajectories but only 70% of failed ones.

Step distribution and difficulty: Failed tasks spike sharply at the 500-step cap, indicating agents exhaust their budget without completing the task. Passed tasks, by contrast, spread across a wide range of step counts. The difficulty distribution shows a large spike in the 0-10 score bin: roughly a quarter of Gemini tasks and a third of Kimi tasks receive near-zero scores, suggesting a substantial fraction of tasks are currently beyond the reach of even frontier models.

Test-Time Auditing (TTA) in detail: Pass rate on CUA-World-Long stays low at 50-100 steps (2.0% to 2.5%), then rises steeply: 6.5% at approximately 200 steps, 7.5% at approximately 400, and 11.5% at approximately 1,300 steps. This sharp jump suggests that most Long tasks require a minimum of 100 steps before any meaningful progress is possible. TTA adds further uplift to 14.0% under the same 2,000-step cap by catching premature stops, where the agent declares it is done but has not actually completed the task.
